# 集成

PiePLM 的设计目标是和制造商已经在用的系统交换数据。本页描述目标集成类别、数据流向，以及保证集成诚实的约束。

项目处于设计阶段，具体连接器尚未实现。下面的模式定义了连接器必须遵守的规则。

## 集成原则

- **每个实体只有一个权威来源**：PiePLM 拥有产品定义和变更历史，不会成为 ERP 的第二份副本。
- **显式映射**：标识符在映射表中维护，不从名称推断。PiePLM 的产品编码映射到 ERP 的物料号，映射关系可见。
- **幂等交换**：每次导入都可以重放而不产生重复。记录携带外部键和校验和。
- **失败可回滚**：导入失败不留下部分记录。批次先暂存、校验，再原子提交。
- **同步可观测**：每次交换记录时间戳、数量和错误摘要，运维人员可以检查。

## CAD 与设计工具

PiePLM 不编辑 CAD 文件。目标集成基于文件和元数据：

- 将导出的 STEP、PDF 和原生文件附加到版本
- 在附件元数据中记录来源应用和版本
- 计算并保存校验和，检测静默修改
- 可选地从 STEP 头信息提取零件号和标题

实时 CAD 插件不在初始设计范围内。它需要按厂商开发插件、桌面运行时和项目目前无法承担的维护负担。

## ERP 与采购

ERP 仍然是采购订单、库存、成本和供应商发票的权威来源。PiePLM 交换：

| 方向 | 数据 |
| --- | --- |
| ERP → PiePLM | 物料主数据引用、供应商身份、单位成本（可选） |
| PiePLM → ERP | 某版本的已发布 BOM、生效日期、变更通知 |
| 双向 | 标识映射与同步状态 |

BOM 导出必须带版本。只发“BOM”不带版本，正是导致制造部门装配错误配置的集成 Bug。

## 质量系统

质量系统拥有不符合项、审核和法规申报。PiePLM 只做关联，不替代它们：

- 不符合项引用产品和版本
- 纠正措施引用解决该问题的变更
- 审核可以查询版本历史和审批记录

如果质量系统是权威来源，PiePLM 只保存引用和摘要，不保存完整副本。

## PieMDM

PieMDM 治理共享主数据。目标集成是关联，不是合并：

- PiePLM 产品 ↔ PieMDM 产品记录
- PiePLM 供应商引用 ↔ PieMDM 供应商记录
- 共享参考数据（单位、国家、分类）从 PieMDM 读取

映射表记录哪个系统对哪些字段有权威。字段级所有权矩阵可以避免两个系统互相覆盖的经典故障。

## PieKBS

PieKBS 为 Agent 提供可检索的蒸馏知识。集成是单向的：

- PiePLM 将文档元数据和（在允许的情况下）文档文本发布到 PieKBS 的 raw 目录或导入端点
- PieKBS 蒸馏文档并索引生成的页面
- Agent 在 PieKBS 搜索，在 PiePLM 读取权威记录

PieKBS 从不写回 PiePLM。知识蒸馏不是受控的数据变更。

## CI/CD 与工程工具

对于把产品数据当作代码管理的团队，目标集成包括：

- 将版本和 BOM 导出为带版本的 JSON，在 PR 中评审
- 在 CI 中用 JSON Schema 校验导出
- 将发布事件推送到 Webhook
- 通过 API 以程序方式比较两个版本

这对已经把配置变更纳入代码评审的 OEM 和工程团队很有用。

## Issue 跟踪器

到 GitHub Issues 或 Jira 的链接是可选的。变更单可以携带外部 Issue 键以便追溯。PiePLM 不镜像 Issue 状态，只保存键，让跟踪器保持权威。

## 文件存储与备份

附件保存在本地磁盘或 S3 兼容对象存储中。集成契约很简单：

- 数据库保存元数据和对象键
- 对象存储保存二进制
- 备份同时覆盖两者并保持一致
- 默认软删除，并设置保留窗口

不要把大型二进制存入数据库，也不要把元数据只放在对象标签里。

## 连接器不得做的事情

- 绕过 API 直接写表
- 自行发明标识而不做映射
- 静默丢弃校验失败的记录
- 没有幂等地重试
- 假设 BOM 没有版本
- 在没有合法依据的情况下复制 ERP 中的个人数据

## 提出集成建议

请开 Issue，包含：

1. 系统名称和版本
2. 要交换的实体和字段
3. 数据流向和预期数据量
4. 需要的失败行为
5. 你是否可以贡献连接器

具体、可测试的方案比在兼容性列表里加一个厂商 Logo 更容易被接受。
