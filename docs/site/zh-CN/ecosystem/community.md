# 社区

PiePLM 是一个由维护者主导的开源项目。背后没有公司、没有销售团队，也没有私有路线图。工作在 GitHub 上公开进行，贡献按技术价值评审。

## 项目在哪里

- **仓库**：[github.com/pieteams/pieplm](https://github.com/pieteams/pieplm)
- **Issue**：[github.com/pieteams/pieplm/issues](https://github.com/pieteams/pieplm/issues)
- **网站**：[pieteams.github.io/pieplm](https://pieteams.github.io/pieplm/)
- **组织**：[github.com/pieteams](https://github.com/pieteams)

GitHub 是唯一的事实来源。没有单独的论坛或聊天频道需要关注。如果一个讨论重要，它应当放在 Issue 里，便于搜索和从文档链接过去。

## 如何贡献

### 文档

最早期的贡献通常是一个更正或澄清。如果某页假设了读者应当知道的知识，或者描述的工作流与你的制造流程不符，请开 Issue 或提交 PR。

### 设计评审

PiePLM 处于设计阶段，这意味着现在挑战模型成本最低。有价值的设计反馈包括：

- 数据模型无法表达真实的产品结构
- 审批流与实际质量或工程流程不符
- API 无法表达某种集成
- 架构忽略了某个部署约束

请带具体例子，而不是个人偏好。

### 代码

等数据模型和 API 规范稳定后，实现类贡献会更有价值。开始大改动前：

1. 开 Issue 描述问题和建议方案。
2. 等待维护者确认范围。
3. 保持 PR 聚焦，把重构与行为变更分开。
4. 为新行为补测试。
5. 在同一个 PR 中更新文档。

拼写错误、坏链接和明显 Bug 等小修复可以直接提交 PR。

### 翻译

本站包含英文和简体中文两个版本。欢迎翻译更正。开始新语言前请先开 Issue，避免重复劳动并保持结构一致。

## 评审与合并策略

- 每个改动在合并前都要评审。
- 维护者可以拒绝超出当前里程碑范围的改动。
- 提交信息沿用仓库的约定前缀（`feat:`、`fix:`、`docs:`、`chore:`）。
- 大型功能在明确里程碑下合并，不在分支中无限累积。

## 治理

项目由维护者主导。决策在公开 Issue 和 PR 中做出，并记录理由。没有投票会员制，也没有基金会。

这种模式在当前规模下换取速度和清晰度。如果贡献者规模扩大，治理方式会在仓库中记录并修订。

## 行为准则

参与者应当直接、具体、尊重他人。批评设计，而不是批评个人。骚扰、人身攻击和持续干扰不被接受。维护者可以锁定或关闭不再有建设性的讨论。

## 安全

不要通过公开 Issue 报告漏洞。使用仓库的 **Security** 标签页，选择 **Report a vulnerability** 提交私有安全公告。请包含复现步骤和受影响的版本或提交。

## 路线图与状态

里程碑在仓库中跟踪。文档诚实说明当前阶段：设计与文档，随后是实现里程碑。项目不承诺日期。

## 支持项目

- 使用这份蓝图，并告诉我们哪里不成立。
- 带复现步骤报告 Bug。
- 改进文档。
- 把项目分享给有相应问题的制造商或咨询顾问。
- 给仓库点 Star，让更多人发现它。

没有付费支持档位，也没有赞助要求。PieTeams 网站上的广告用于覆盖托管成本。
