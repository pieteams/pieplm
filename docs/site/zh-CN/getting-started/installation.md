# 安装

PiePLM 尚未发布可运行的版本，因此目前没有可以执行的安装命令。本页记录的是目标安装模型和设计所要求的依赖，帮助你在第一个版本发布前评估运维负担。

## 设计目标：一台服务器，少量组件

目标部署是单个 Go 服务加 PostgreSQL。核心产品不需要消息队列、Kubernetes Operator 或外部搜索集群。一家小型制造商应当能在一台普通服务器上运行系统，或者在笔记本上做评估。

可选组件就是可选的：

| 组件 | 是否必需 | 用途 |
| --- | --- | --- |
| PiePLM 服务 | 是 | API、工作流、搜索与 Web UI |
| PostgreSQL 15+ | 是 | 关系数据、全文检索、审计历史 |
| 对象存储（S3 兼容或本地磁盘） | 否 | 大型 CAD 文件与附件 |
| 反向代理 | 否 | TLS 终止与域名路由 |
| PieKBS | 否 | 为 Agent 提供蒸馏后的文档知识 |
| PieMDM | 否 | 产品与供应商的共享主数据 |

## 前置条件

- 一台 Linux 服务器、macOS 或 Windows 机器（带 Docker），或者用于源码构建的 Go 工具链
- PostgreSQL 15 或更高版本
- 小团队建议 2 核 CPU、4 GB 内存；文件存储较大时相应增加
- 一个用于数据库和附件卷的备份目标

目标 Docker 路径只要求可用的 Docker Engine 和 Docker Compose。源码路径的目标工具链是 Go 1.25+。

## 目标部署方式

### Docker Compose

仓库将提供包含服务和 PostgreSQL 容器的 Compose 文件。配置通过环境变量和挂载的配置文件提供。这是评估和小规模生产部署的推荐路径。

### 单一二进制

服务计划编译成单个二进制，并内嵌 Web 资源。这适合已经运行 PostgreSQL、希望用 systemd 或类似工具管理进程的团队。

### 托管 PostgreSQL

如果组织已经有托管 PostgreSQL 服务，可以直接指向它。数据库是唯一有状态的依赖；附件可以放在本地磁盘或对象存储。

## 计划中的首次启动流程

第一个版本计划按以下顺序启动。请把它当作设计说明，而不是可以直接复制的命令。

1. 启动 PostgreSQL，为 PiePLM 创建数据库。
2. 通过环境变量提供数据库连接、服务端密钥和初始管理员账号。
3. 启动服务。首次启动时应用迁移并创建初始 Schema。
4. 使用初始管理员登录，并立即修改密码。
5. 创建组织、业务单元和第一批用户账号。
6. 配置认证（初期为本地账号；OIDC 是后续里程碑）。
7. 创建一个产品并附加第一份文档。
8. 配置变更工作流和审批角色。

## 配置原则

配置应当是显式的、有文档的、可被环境变量覆盖的。目标约定：

- 环境变量使用 `PIEPLM_` 前缀
- 结构化设置使用 YAML 文件，环境变量优先
- 密钥永不进入仓库
- 提供 `/healthz` 存活检查和 `/readyz` 数据库就绪检查

详细设置见[配置参考](/zh-CN/reference/config)。

## 验证

当版本发布后，安装应当无需阅读源码即可验证：

- 服务启动并报告数据库连接正常
- 迁移完成，无需手工执行 SQL
- 管理员可以登录并创建产品
- API 能通过有文档的端点返回刚创建的产品

任何一项失败，该版本就不适合生产使用。

## 升级与备份

目标升级路径是随每个版本发布的前向迁移。升级前请：

1. 备份 PostgreSQL 数据库。
2. 备份附件卷或对象存储前缀。
3. 阅读发布说明中的迁移警告。
4. 应用新版本并执行一次迁移命令。
5. 验证健康状态并登录。

初始设计不支持降级路径。这是有意的约束：可逆迁移很难保证，也非常容易出错。

## 明确不在范围内

为了让第一个版本足够小，以下内容不在初始版本计划中：

- 高可用集群
- 多区域复制
- 插件市场
- 移动端应用
- CAD 文件编辑

系统应当与这些能力集成，而不是重新实现它们。
