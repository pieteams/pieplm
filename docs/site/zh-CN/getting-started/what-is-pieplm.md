# 什么是 PiePLM?

**PiePLM** 是一份面向中小制造商的、开放且文档先行的产品生命周期管理（PLM）设计蓝图。它定义一个范围克制、运维负担低的系统，用来保持需求、设计、物料清单（BOM）、变更、质量记录和供应商数据的一致性。

PiePLM 目前处于**设计与文档阶段**。公开仓库包含问题陈述、市场调研、架构笔记和模块设计，尚无可以运行的发行版本。本页说明项目想成为什么，也同样说明它明确不想成为什么。

## 面临的问题

传统 PLM 系统给中小企业带来显著挑战：

- **高昂成本**：许可、实施与持续运维的费用按大型组织定价
- **复杂性**：漫长的上线周期、专职管理员和僵化的流程
- **架构僵化**：难以适配小团队真实的工作方式
- **数据孤岛**：产品信息散落在共享盘、电子表格和 ERP 中

结果是可以预见的：图纸与 BOM 脱节，变更原因丢失，供应商记录重复，审计只能靠人工翻查。企业知道问题存在，但市面上的软件比企业本身还庞大。

## 目标方案

PiePLM 用刻意收窄的范围来解决问题：

| 能力 | 实际含义 |
| --- | --- |
| **产品身份** | 每个产品一条记录，有明确负责人和生命周期状态 |
| **版本快照** | 已发布版本不可变；修改产生新版本 |
| **文档控制** | 图纸、规范和报告关联到版本，并记录校验和 |
| **结构化 BOM** | 带版本的树形结构，而不是附件里的电子表格 |
| **受控变更** | 变更单记录原因、影响、审批和产生的新版本 |
| **需求追溯** | 需求关联到设计与测试证据 |
| **质量与供应商关联** | 不符合项和供应商引用受影响的产品与版本 |
| **API 与 MCP** | 同一契约服务 UI、系统集成和 AI Agent |

注意这里没有：项目组合管理、项目治理、仿真数据管理、多工厂配置和插件市场。这些都是合理的 PLM 议题，但不是一家三十人制造商最先要解决的问题。

## 设计哲学

1. **先窄后宽**：先把一个产品记录、一份 BOM 和一条变更流做好，再考虑增加模块。
2. **显式优于隐式**：关系使用标识符和带版本的记录，而不是文件夹名和邮件线程。
3. **朴素基础设施**：Go 与 PostgreSQL，可部署在一台服务器上。不强制依赖消息队列或搜索集群。
4. **数据可读**：Schema、迁移脚本和 API 定义都在仓库里，始终可以导出。
5. **安全的自动化**：Agent 默认只读；机器可以起草变更，人负责批准。
6. **诚实的文档**：设计文档不应该假装自己是已发布的产品。

## 与其他 PieTeams 项目的关系

- [PieMDM](https://pieteams.github.io/piemdm/) 治理跨系统的产品、供应商、物料等主数据。PiePLM 聚焦产品定义及其生命周期。
- [PieKBS](https://pieteams.github.io/piekbs/) 将文档蒸馏为 Agent 可检索的知识库。PiePLM 存储权威的结构化记录，PieKBS 存储叙述性知识和原始材料。

三者可以独立采用。组合使用时，它们形成一条从产品定义到主数据治理再到可检索知识的链路。

## 状态与路线图

项目正按设计里程碑推进：

1. 问题陈述与范围（已发布）
2. 市场与系统调研（已发布在本站）
3. 架构与模块边界（已发布）
4. 数据模型与 API 规范（进行中）
5. 核心模块实现（尚未开始）
6. 基于 Docker 的参考部署（计划中）

里程碑和设计讨论在 [GitHub 仓库](https://github.com/pieteams/pieplm) 中跟踪。项目不承诺具体日期，由维护者主导，并欢迎贡献。

## 适用对象

- 正在评估开源替代方案是否可信的**中小制造商**
- 需要为小客户提供轻量参考模型的 **PLM 咨询顾问**
- 愿意参与开源 PLM 实现的**开发者**
- 希望在采购软件前先理解问题的**技术团队**
