# 核心模块

PiePLM 围绕少量领域模块组织。每个模块拥有自己的数据、发布自己的接口，并可以逐步采用。模块边界很重要：如果一个模块直接读另一个模块的表，它就很难被替换。

本页描述目标模块、各模块拥有的数据以及它们如何交互。实现仍在进行中，但模块边界是设计中相对稳定的部分。

## 模块地图

| 模块 | 拥有的数据 | 依赖 |
| --- | --- | --- |
| **产品** | 产品身份、生命周期状态、负责人 | — |
| **版本** | 版本快照、生效规则、发布状态 | 产品 |
| **文档** | 附件、元数据、校验和、文档类型 | 产品、版本 |
| **BOM** | 结构化物料清单、零件引用、替代件 | 产品、版本 |
| **需求** | 需求、验收标准、追溯关系 | 产品、版本 |
| **变更** | 变更单、影响分析、审批 | 产品、版本、BOM |
| **质量** | 不符合项、纠正措施、与版本的关联 | 产品、版本 |
| **供应商** | 供应商记录、资质、零件来源 | 产品 |
| **平台** | 身份、角色、工作流引擎、审计日志、搜索 | 所有模块 |

## 产品

产品模块刻意保持轻量。它拥有稳定身份和生命周期状态机（`development`、`active`、`phase-out`、`obsolete`），不拥有版本内容。

为什么把产品和版本分开？因为身份和内容的变化频率不同。一个产品编码可能使用十年，而它的版本内容每隔几个月就会变化。混在一起会导致身份重复或历史丢失。

## 版本

版本发布后就是不可变快照。它记录：

- 版本标识（`A`、`B`、`1`、`2` 或客户约定的编号）
- 生效方式（立即、按日期或按序列号）
- 属于该版本的文档和 BOM
- 发布该版本的审批记录

草稿版本可以编辑，已发布版本不可以。发布后的更正必须通过变更模块创建新版本。

## 文档

文档模块保存元数据和二进制文件的引用。它拥有：

- 文件名、媒体类型、大小和校验和
- 存储位置（本地路径或对象键）
- 文档类型（图纸、规范、测试报告、证书、其他）
- 产品与版本关联
- 上传和评审元数据

初始设计不解析或渲染 CAD 文件。查看功能交给客户端或后续集成。

## BOM

BOM 模块拥有产品结构：

- 带稳定标识的行
- 零件或产品引用
- 数量、单位和位置号
- 替代件和等效件
- 从版本继承的生效规则

BOM 随版本一起版本化，不是漂浮的电子表格。修改已发布的 BOM 必须经过变更模块，由它创建新版本。

## 需求

需求模块记录产品必须做到什么，并把它关联到设计和测试证据。一条需求包括：

- 标识和陈述
- 分类（功能、安全、法规、商务）
- 优先级和验证方式
- 指向文档、BOM 行和测试的追溯链接

初始实现刻意不引入完整的质量管理方法论。目标是让小团队可追溯，而不是做合规表演。

## 变更

变更模块是修改已发布版本的唯一路径。变更单记录：

- 改什么
- 为什么改（原因和证据）
- 受影响的产品、版本、BOM 行和文档
- 影响分析（维修包、未结订单、供应商）
- 审批人及时间戳

审批是工作流。工作流引擎属于平台服务；变更模块定义状态和所需角色。批准后，变更生成新版本并回链到变更单。

## 质量

质量模块记录不符合项和纠正措施。每条记录关联到受影响的产品和版本，使质量数据成为产品历史的一部分，而不是孤立的工单队列。

初始范围之外：完整 CAPA 流程、审核管理和法规申报。数据模型为这些能力预留空间。

## 供应商

供应商模块保存供应商身份、联系信息、资质状态及其供应的零件。它刻意不是完整的采购系统。采购订单和发票属于 ERP。

## 平台服务

平台模块提供跨领域能力：

- **身份与访问**：用户、角色、权限、API Key
- **工作流**：状态、流转、审批人、升级提醒
- **审计**：只追加的写入与审批记录
- **搜索**：跨实体索引（见[搜索引擎](/zh-CN/guide/search-engine)）
- **文件**：附件存储抽象

把这些服务独立出来，可以避免每个领域模块自己发明权限模型或审计格式。

## 采用顺序

务实的推进顺序：

1. 产品 + 版本 + 文档：先把一个产品记录做对
2. BOM：替换主电子表格
3. 变更：用轻量流程引入受控变更
4. 需求：只对新产品的需求做追溯
5. 质量 + 供应商：把现有记录关联到版本

每一步都应当独立产生价值。如果某一步需要另外三个模块才能有用，说明范围划得太大。

## 边界规则

为了保持模块可替换：

- 模块不得直接读另一个模块的表，只能调用接口。
- 共享关注点放在平台服务中，不复制到每个模块。
- 状态变化发布事件，消费者不轮询表。
- 每个模块拥有自己的迁移脚本和 API 资源。
- 跨模块报表使用读模型，不在所有权边界上做临时 join。

这些规则比单一巨型 Schema 的前期成本高，但当第一个模块被替换或拆分时，会得到回报。
